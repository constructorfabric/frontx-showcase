## 1. Overview

The template-site DESIGN is decomposed into eight features along its eight components: the two parts of the shared folder `shared/site/` that carry behaviour of their own (site navigation, content model), the two concerns every package repeats (the screen package frame and, in the three data packages, the data services) and the four screens (home, templates, docs, libraries). Each feature owns exactly one component, so the boundary of a feature is the boundary its component has in the DESIGN. The look of every page comes from outside the template: the blocks of template-site-blocks, the kit candidates of template-kit-candidates, the brand of template-site-brand and the UI kit, reached as named packages; the template itself carries no stylesheet.

The cut differs from the starting list of the adoption plan in two places, both forced by the DESIGN's component model: the screen frame (the theme helpers in `shared/site/theme/`, each package's `src/shared/`, its lifecycle, its build and the template overlay) and the data services (each content package's `src/api/` and app setup) are DESIGN components of their own, repeated byte-identical or in the same form across the packages. Giving each its own feature lets one FEATURE specify the repeated behaviour once and place the same markers in every copy, instead of four screen FEATUREs specifying it four times.

Code scope rules used below. Paths are relative to `template-site/src-app/mfe_packages/`, and `site-*-mfe` means each of the four packages. A file belongs to exactly one feature. Tests (`*.test.*`), `test-support/`, `vite.config.*` and `vitest.config.*` belong to the feature whose package code they test or configure and are excluded from marker scanning by the repository registry's ignore list. The composed copies of these packages under `site/src-app/mfe_packages/` are produced by the repository's composition step and are not part of this template's code; they are covered by the [repository DESIGN](../../architecture/DESIGN.md), not here. The site data the content screens show is generated by the repository's site data tooling and the plain-text twins are written by the metadata tooling of [template-site-meta](../../template-site-meta/architecture/DESIGN.md); this decomposition covers only the template's side of those contracts.

Priorities: `p1` for the foundation features the screens build on, `p2` for the screens.

### 2.1 [Site Links](features/site-links/) - HIGH

- [x] `p1` - **ID**: `cpt-template-site-feature-site-links`

- **Purpose**: Open another screen, or a page of it, from a link of the template through FrontX actions only (the screen domain's mount action, then the show action the target declares), with no address in the link, the link role and keyboard activation; handle the docs and templates screens' show actions; and move focus with in-page jumps.

- **Depends On**: None

- **Scope**:
  - The site link component for every link form (another screen by its extension id with an optional show action, a route inside the current screen, a heading anchor, an external address)
  - The link element to another screen: no address, the link role, the tab order, a click or Enter dispatches the chain
  - Opening a screen: the mount action on the screen domain with the target's show action as the chain's next step
  - The show action handler and its registration helper, which maps the payload to the screen's own route and replaces the entry through its app's navigation facade
  - The ids of the template's screens and their show actions, and the catalogue screen's id the libs screen opens
  - Heading jumps that scroll to the heading and move keyboard focus to it
  - Code: `shared/site/navigation/**` (`SiteLink.tsx`, `openScreen.ts`, `siteScreens.ts`, `jump.ts`)

- **Out of scope**:
  - Calling the registration helper from each lifecycle's `mount()` (screen package frame)
  - Declaring the show action and its schema in each manifest (each screen feature owns its `mfe.json`)
  - Writing the page address, listing the registered screens (the host)
  - The twin link form and its document-relative address (content model)
  - The repository-level contract of the screen actions and the show actions of other templates, described in the [repository DESIGN](../../architecture/DESIGN.md)

- **Requirements Covered**:

  - [x] `p1` - `cpt-template-site-fr-cross-screen-links`
  - [x] `p1` - `cpt-template-site-fr-show-page`
  - [x] `p2` - `cpt-template-site-fr-mount-independent-links`
  - [x] `p2` - `cpt-template-site-fr-in-page-jumps`

- **Design Principles Covered**:

  - [x] `p1` - `cpt-template-site-principle-actions-not-addresses`

- **Design Constraints Covered**:

  - [x] `p1` - `cpt-template-site-constraint-query-addressing`
  - [x] `p2` - `cpt-template-site-constraint-no-screen-list`
  - [x] `p2` - `cpt-template-site-constraint-unknown-mount-point`

- **Domain Model Entities**:
  - Link target
  - Site screen

- **Design Components**:

  - [x] `p1` - `cpt-template-site-component-site-navigation`

- **API**:
  - `mount_ext` on the screen domain

## 3. Feature Dependencies

```text
cpt-template-site-feature-site-links  (foundation)
cpt-template-site-feature-data-services          (foundation)
    |
    +--> cpt-template-site-feature-content-model
    |        (site-links)
    +--> cpt-template-site-feature-screen-frame
    |        (site-links, data-services)
    |
    +--> cpt-template-site-feature-home-screen
    |        (screen-frame, content-model, site-links)
    +--> cpt-template-site-feature-templates-screen
    +--> cpt-template-site-feature-docs-screen
    +--> cpt-template-site-feature-libraries-screen
             (each: content-model, data-services, screen-frame)
```

**Dependency Rationale**:

- `cpt-template-site-feature-site-links` and `cpt-template-site-feature-data-services` depend on nothing in the template: the DESIGN's dependency rules make navigation a leaf of the shared folder, and the data services stand on FrontX and template-shell only. They can be developed in parallel.
- `cpt-template-site-feature-content-model` requires `cpt-template-site-feature-site-links`: the renderer draws links with the site link; its blocks, kit candidates and brand art come from the named packages of other templates.
- `cpt-template-site-feature-screen-frame` requires `cpt-template-site-feature-site-links` (the docs and templates lifecycles register their show action handler) and `cpt-template-site-feature-data-services` (a content package's lifecycle renders over the app its setup creates).
- `cpt-template-site-feature-home-screen` requires `cpt-template-site-feature-screen-frame`, `cpt-template-site-feature-content-model` and `cpt-template-site-feature-site-links`; it reads no site data.
- `cpt-template-site-feature-templates-screen`, `cpt-template-site-feature-docs-screen` and `cpt-template-site-feature-libraries-screen` each require `cpt-template-site-feature-content-model`, `cpt-template-site-feature-data-services` and `cpt-template-site-feature-screen-frame`; the four screens are independent of each other and can be developed in parallel.
- Shared coverage, stated explicitly: `cpt-template-site-fr-screen-registration`, `cpt-template-site-fr-not-found`, `cpt-template-site-fr-page-metadata` and `cpt-template-site-nfr-description-length` are covered by each of the four screen features, because each screen declares its own extension, metadata and not-found page in its own package; `cpt-template-site-nfr-truthful-content` is covered by the home and libraries screens, the two whose strings state facts and comparisons. Every DESIGN component, principle, constraint and sequence is in exactly one feature.
