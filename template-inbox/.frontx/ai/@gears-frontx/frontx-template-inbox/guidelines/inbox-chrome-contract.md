# Guideline: What the Shell Owns and What Each Inbox Screen Keeps

Each inbox screen is a microfrontend package the application shell mounts into a shadow root in its screen domain. The shell draws the chrome; the screen keeps everything a page would otherwise get from its own document. Paths below are relative to `src-app/mfe_packages/`.

## The shell owns

- **The menu.** A screen appears there through the screen extension in its package's `mfe.json` (`route`, and `presentation.label`, `icon`, `order`); there is no menu list to edit. The inbox screens sit in the site host's demos group: each extension is a plain screen extension of the shell's screen type `gts.frontx.mfes.ext.extension.v1~frontx.screensets.layout.screen.v1~`, with an id of the form `gts.frontx.mfes.ext.extension.v1~frontx.screensets.layout.screen.v1~frontx.inbox_<x>.screens.<x>.v1`, and names the group in `presentation.group` by its nav group instance id, `gts.frontx.screensets.layout.nav_group.v1~frontx.site.layout.demos.v1`, an instance of the shell's nav group type (`gts.frontx.screensets.layout.nav_group.v1~`; template-site's `menu-groups` guideline). The manifest carries no screen type schema. The label in `mfe.json` is the menu's; the screen's own name for itself is `nav_label` in its catalogue.
- **The page address.** The shell writes a screen's token into the URL (`/?screen=inbox-contacts`) and resolves it back on load, Back and Forward. The token equals the extension's `route` without its slash and is listed in `shared/inbox/navigation/screens.ts` (`INBOX_SCREENS`); `inbox-contacts-mfe/src/shared-inbox/screens.test.ts` holds every package's manifest to that list.
- **Layout, theme and language.** The sidebar, header and the area a screen fills are the shell's. The theme and the language reach a screen as shared properties on its bridge (`FRONTX_SHARED_PROPERTY_THEME`, `FRONTX_SHARED_PROPERTY_LANGUAGE`).
- **The host stylesheets.** `ThemeAwareReactLifecycle` adopts them into the shadow root and paints `:host` from `var(--foreground)` and `var(--background)`.

## Each screen keeps

The package's `src/lifecycle.tsx` exports a subclass of `InboxScreenLifecycle` (`shared/inbox/lifecycle/InboxScreenLifecycle.tsx`) passing its app, catalogues and route tree. The base class puts the kit's tokens on the shadow host once per shadow root (`anchorKitThemeOnShadowHost`, a style node marked `data-kit-theme`) and renders the screen inside `InboxScreenFrame` (`shared/inbox/lifecycle/InboxScreenFrame.tsx`), which keeps:

- **`data-theme`** on the frame, from the shell's theme through `kitThemeScopeFor` (`kitThemeScope.ts`). Without it kit tokens inherit the shell's `:host` colours or the system scheme. A dark host theme the shell adds must join `DARK_HOST_THEMES` there.
- **`dir`** on the frame and on the shadow host, from the language (`useHostDirection.ts`). Package CSS uses logical properties only (`inset-inline-end`, `margin-inline-start`, `border-inline-end`, `text-align: end`).
- **The portal container**, the frame's first child (`data-inbox-portal`), handed out by `usePortalContainer()` from `screenContext.ts`. Every popup (sheet, dialog, select, menu, combobox) passes it as `container`, so it renders inside the shadow root, styled and focus-trapped.
- **No document title or head tags.** The site's head-sync owns the document head and applies each screen's `seo` block from its `mfe.json`; the frame never writes `document.title`.
- **Heading focus.** Every screen renders exactly one `h1` through `ScreenHeading` (`shared/inbox/ui/ScreenHeading.tsx`). Every mount of the frame asks that heading to take focus (`requestScreenHeadingFocus()` in a mount effect of `InboxScreenFrame`); the frame reads nothing outside the screen's container for it. Inside a screen, the root route component calls `useRouteFocus(pageKey)` so a change of page (directory to a person and back) moves focus too.
- **The error boundaries.** Each root route component wraps the screen's pages in `ScreenRouteBoundary` (`shared/inbox/ui/ScreenRoutes.tsx`: `SinglePageRoot`, or `ScreenRoot` for a screen with several pages), a `ScreenErrorBoundary` keyed on the pages the screen's own router matched: a render failure shows a kit `Alert` whose only button is "Try again", which renders the screen afresh, while the shell and its menu keep working (the screen never reloads the page, which is the host's), and moving to another page of the screen clears it. The frame keeps one more boundary around the router itself. No inbox code reads the page address; leaving the screen remounts it. A failed query is not an error for it; the screen shows `LoadErrorPane`.
- **The router.** The framework's `<ExtensionRouter>` over the registry of the package's own app (`microfrontends()` in `buildInboxScreenApp`), which places the screen's own paths in the `route=` parameter of its entry (`/?screen=inbox-contacts;route=r-42` opens the contacts route `$contactId`). An address the route tree does not match renders the screen's own not-found page, `ScreenNotFound` from `shared/inbox/ui/ScreenRoutes.tsx` as the root route's `notFoundComponent`. The routing packages are shared dependencies of every package (`sharedDeps` in its `vite.config.ts`) and deduped like the kit (`resolve.dedupe` there and in `vitest.config.ts`, and each package's `tsconfig.json` `paths`), so the framework's router and a screen's `useNavigate` are one copy.
- **Translations.** Each package's catalogues are the `<lang>.json` files of `src/screens/<screen>/i18n/`, the shared components' the `<lang>.json` files of `shared/inbox/i18n/`, both read by `import.meta.glob` so a new language is only new files. `useInboxTranslate` merges the package's catalogue over the shared one for the shell's language, falling back to `en` as a whole when either layer lacks it; components read `useInboxT()`.

- **The layout width.** The frame root is the `inbox-screen` size container, and `useContainerMeasure` measures it, so the panes follow the room the shell leaves beside its sidebar, never the viewport. The frame renders the routes only after that first read, in the layout effect before the first paint, so a screen never mounts in a layout its width does not have. JavaScript decisions (single pane, the side column as a sheet) read `useScreenLayout()`; stylesheets use `@container inbox-screen (width < Nrem)` rules on the widths in `SCREEN_BREAKPOINTS_REM` (`shared/inbox/ui/screenLayout.ts`), and no pane rule is a width media query.

Layout inside the screen uses the blocks in `shared/inbox/blocks/` (`NavColumn` for the side column with `useSidebarToggle`, `ListPane` and `ThreadListItem`, `DetailPane`, `ThreadPane`, `ReplyComposer`, `PagePane`, `PaneState` and the others, each with a card `<Block>.md`) and the breakpoint table in `shared/inbox/ui/screenLayout.ts`, components from `@gears-frontx/ui-kit`, and the kit candidates from `@gears-frontx/kit-candidates` for typography, description lists and titles that are the screen's heading. A screen component imports no stylesheet: a new arrangement is a new block (or a part of one) with a layout-only stylesheet on kit tokens, and a declaration it needs for a kit gap is a row of `shared/inbox/blocks/styles-exemptions.json` naming the gap. A list of rows on the kit's `ItemGroup` puts each row in a list item (`ListPaneGroup` and `NavColumn` do).

## Opening another screen

`openScreen(bridge, { screen, action })` in `shared/inbox/navigation/openScreen.ts` sends one actions chain through the caller's bridge: the screen domain's `mount_ext` with the target's extension id (`INBOX_SCREEN_EXTENSIONS` in `screens.ts`), then, for a page, the action the target declares, to the mounted target. Contacts declares `show_contact` (`SHOW_CONTACT_ACTION`, payload `{ contact }`) in its entry's `actions` with a closed schema in `mfe.json` (`schemas`; target: the contacts screen only) and registers `ShowContactHandler` in its lifecycle's `mount()` before returning. The framework router writes the target's entry, and the handler replaces it with the person's page through its app's navigation facade (`app.mfeRouter.navigation().replace`), encoding the id as one path segment, so the result is one history entry and Back returns to the caller as it was. A screen never names another screen's routes and never writes the address. Chat's "View contact" is `openScreen(bridge, { screen: INBOX_SCREENS.contacts, action: { type: SHOW_CONTACT_ACTION, payload: { contact: contactId } } })` (`inbox-chat-mfe/src/screens/chat/chatNavigation.ts`). It returns `false` when the caller does not occupy the shell's screen domain (`isInScreenDomain`), and the caller then does not offer the link. Screens never import each other's code; only `shared/inbox/` is shared.

## Menu order bands

| Screen | Package | Token | Order |
|---|---|---|---|
| Contacts | `inbox-contacts-mfe` | `inbox-contacts` | 61 |
| Dashboard | `inbox-dashboard-mfe` | `inbox-dashboard` | 62 |
| Chat | `inbox-chat-mfe` | `inbox-chat` | 63 |
| Mail | `inbox-mail-mfe` | `inbox-mail` | 64 |

Every inbox screen names the demos nav group (`gts.frontx.screensets.layout.nav_group.v1~frontx.site.layout.demos.v1`) in `presentation.group`, so the shell's navigation folds them into the demos group, at orders 61 to 64 among the group's screens (calendar 60, the MFE demo 65 to 67 and 69). The site's header lists the group as one entry at the order of its first screen, 60, after the site's top-level entries (home 10, templates 20, UI kit 30, blocks 31, libraries 35, docs 40). A screen added beside them takes the next free order; a tie orders by the shell's own rule, which is harmless but worth avoiding in a product menu.

## Adding a screen

Scaffold the package with the MFE template's `add-mfe-package` skill, then make it an inbox screen: a lifecycle subclass of `InboxScreenLifecycle`, the `@inbox-shared` alias, the dedupe list and the routing packages in `sharedDeps` written into its `vite.config.ts` and `vitest.config.ts` as the other packages have them, its token in `INBOX_SCREENS`, its registrars and its app from `buildInboxScreenApp` in `src/init.ts` (see the inbox data contract guideline), and the setup in `src/test-support/setup.ts` calling `registerInboxTestSetup` from `shared/inbox/test-support/setup.ts`. A one-page screen's root route is `SinglePageRoot` and its `notFoundComponent` renders `ScreenNotFound` (`shared/inbox/ui/ScreenRoutes.tsx`); its screen suites stand in for the query layer through `createApiMocks` (`shared/inbox/test-support/apiMocks.ts`) over its own endpoint map, and `src/screens/<screen>/i18n/catalogue.test.ts` calls `describeScreenCatalogue` (`shared/inbox/test-support/describeScreenCatalogue.ts`); `src/manifest.test.ts` calls `describeScreenManifest` (`shared/inbox/test-support/describeScreenManifest.ts`).

## Where the shared tests run

`shared/inbox/` has no `package.json`, so its tests run in a package: `inbox-contacts-mfe/src/shared-inbox/`. Three of them read the sibling packages: `screenLayout.test.tsx` reads every stylesheet of the shared folder (the blocks') and of `inbox-*-mfe/src/` through `import.meta.glob` to hold the container rules to the breakpoint table, `screens.test.ts` reads every `inbox-*-mfe/mfe.json` the same way to hold the manifests to `INBOX_SCREENS`, and `dataLayer.test.ts` lists the `inbox-*-mfe` folders present and scans their sources and the shared folder's for the FrontX data and state layers. Each holds whichever packages a project keeps, so dropping a screen leaves them passing. A project that drops the contacts screen moves that folder into a package it keeps, or the shared folder loses its coverage.
