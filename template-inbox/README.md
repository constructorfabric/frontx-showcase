# template-inbox

Four helpdesk-style screens for a FrontX application, as a FrontX template.

## What it contributes

Four microfrontend packages the shell mounts in its screen domain, built from `@gears-frontx/ui-kit` and the kit candidates `@gears-frontx/kit-candidates` with mocked `@gears-frontx/api` services, their shared folder, and the AI bundle `.frontx/ai/@gears-frontx/frontx-template-inbox/` with two guidelines (`inbox-data-contract`, `inbox-chrome-contract`). All paths are under `src-app/mfe_packages/`:

- `inbox-contacts-mfe`: a filterable, sortable directory and each person's page.
- `inbox-dashboard-mfe`: KPI cards, charts, team workload, a stage funnel, conversion by source and the recent-activity table.
- `inbox-chat-mfe`: channels, the conversation list, the thread with a reply-and-note composer, the customer-details panel and "View contact".
- `inbox-mail-mfe`: mailboxes, the mail list with search, the reading pane with history and reply, and compose.
- `shared/inbox/`: what the four share, imported as `@inbox-shared/*` and bundled into each package: the API services, mock store and query hooks (`api/`), the shared catalogue (`i18n/`), the screen lifecycle and frame (`lifecycle/`), cross-screen navigation (`navigation/`), shared components (`ui/`), the blocks every screen draws its panes, lists, threads, composers and cards with (`blocks/`, each with a layout-only stylesheet, a card and a test, and the exemptions ledger `styles-exemptions.json`) and the test platform (`test-support/`). Screen components import no stylesheet. It has no `package.json` and is not a workspace. Packages never import one another.

Contacts, dashboard and chat read `InboxApiService` (`/api/inbox`), answered from the inbox mock store in `shared/inbox/api/mockStore.ts`; every package that bundles it keeps its own copy of the state, created from the same seed and kept across the screen's remounts until the page reloads. A write is in the state of the package that made it, so that screen shows it once its own read has answered, also after a remount; the contacts screen answers from its own copy of the seed. The packages read the same endpoints under the same query keys (`[baseURL, method, path]`) in the host's one shared query cache (`queryCacheShared()`), and every mount refetches in the background, so reads also pass between packages through that cache: after chat posts a reply, the contacts screen first paints the cached answer chat filled, reply included, until its own mount refetch answers from its own copy of the seed and the reply disappears there; a return to chat can briefly paint contacts' answer until chat's refetch brings the reply back. A real backend gives one set of facts to every screen; the mocks do not simulate that. The dashboard's overview service (`/api/dashboard`) and the mail service (`/api/mail`, with its own package mock state in `mailMockStore.ts`) live in their packages. Each package switches its mocks on with `mock({ enabledByDefault: true })` in the app every `src/init.ts` builds with `buildInboxScreenApp` (`shared/inbox/lifecycle/screenApp.ts`, which adds `mock()` before `queryCacheShared()` so a package loading for the first time keeps the shared cache, a FrontX limitation of `queryCacheShared()`); `false` sends every request to a real backend with the endpoints and screens unchanged. The screens read and write through `useApiQuery` and `useApiMutation` of `@gears-frontx/react` over the page's shared query cache, every service declares the shell's `RestMockPlugin`, and what a screen keeps across mounts is a FrontX slice of its package. The `inbox-data-contract` guideline has the endpoints, the shared cache and its invalidations, the slices and the backend switch; `inbox-chrome-contract` has what the shell owns and what each screen keeps.

## Prerequisites

A project with template-shell, template-mfe and template-kit-candidates applied (the shell supplies the host, the screen domain, `src-app/vitest.mfe.base.ts`, `src-app/__test-utils__/` and the `frontxMfGts()` build plugin; template-kit-candidates delivers the workspace package `@gears-frontx/kit-candidates`). The packages pin `@gears-frontx/kit-candidates` `0.1.0-alpha.0`, `@gears-frontx/ui-kit` `0.4.0`, `@gears-frontx/routing` `0.3.0`, `@gears-frontx/routing-tanstack` `0.3.0`, the shell's workspace versions, `lucide-react` `1.33.0` and (dashboard) `recharts` `3.10.1` exactly.

## Screens and routes

| Token | Package | Internal routes | Menu | Port |
|---|---|---|---|---|
| `inbox-contacts` | `inbox-contacts-mfe` | `/` (directory), `/$contactId` (a person's page) | 61 Contacts | 3010 |
| `inbox-dashboard` | `inbox-dashboard-mfe` | `/` | 62 Dashboard | 3020 |
| `inbox-chat` | `inbox-chat-mfe` | `/` | 63 Chat | 3030 |
| `inbox-mail` | `inbox-mail-mfe` | `/` | 64 Mail | 3040 |

Addresses: `/?screen=inbox-contacts`, a person: `/?screen=inbox-contacts;route=<id>`. Each screen renders its route tree through `<ExtensionRouter>`; an address its tree does not match renders the screen's own not-found page. Chat's "View contact" opens the person's page in contacts through `openScreen` (`shared/inbox/navigation/openScreen.ts`): the screen domain's `mount_ext` opens contacts, and contacts' own `show_contact` action (`gts.frontx.mfes.comm.action.v1~frontx.inbox_contacts.action.show_contact.v1~`, payload `{ contact }`, the person's id) shows the person's page. Contacts declares the action and its closed schema in its `mfe.json` and registers the handler when it mounts. One history entry; Back returns to the chat.

## SEO metadata

Declared once per screen, in the `seo` block of its extension in each package's `mfe.json` (`title`, `description`). Contacts declares `seo.routes["/$contactId"]` with `indexable: false`: a person's page is a pattern, not one page. Each package's `src/manifest.test.ts` holds the declaration to its route tree.

## Develop

Edit the files here, never the copies under `site/`. From the repository root:

```bash
npm run site:assemble             # copy into site/
npm install --prefix site         # once, after adding or renaming a package
npm run dev                       # http://localhost:5173/?screen=inbox-contacts
```

`npm run site:assemble -- --check` reports any difference between this template and the site copy. The shared folder's tests run inside `inbox-contacts-mfe/src/shared-inbox/`; three of them read the sibling packages (`screenLayout.test.tsx` their stylesheets and `screens.test.ts` their `mfe.json` through `import.meta.glob`, `dataLayer.test.ts` the sources of every `inbox-*-mfe` folder present), and each holds whichever packages a project keeps.

Kit gaps the screens work around (each declaration a block keeps for one is a row of `shared/inbox/blocks/styles-exemptions.json`):

- In the light theme the `success` (3.43:1) and `danger` (4.28:1) badge tones stay under the 4.5:1 text contrast the design guardrails ask for; the badge text carries the meaning.
- The kit's `ItemGroup` takes the list role, and a row rendered as a button cannot be its list item, so each row sits in a list item box that lays nothing out; the design guardrails report a control-height mismatch (36 px controls beside 65 px rows) on the mail lists.
- No pane chrome, no `Sidebar` that sits in a bounded container, no Item density between `xs` and `sm`, no selected row state, no title tone for a read row.
- `Bubble` has no variant with the tail corner at the bottom and no trailing time inside the bubble; the transcript block sets both.
- No chart size on `ChartContainer` (it fixes `aspect-ratio: 16 / 9`) and no tokens for the dashboard's big-number type scale.

## Moving into another project

Copy the four package directories, `shared/inbox/` and `.frontx/ai/@gears-frontx/frontx-template-inbox/` into a project that has template-shell, template-mfe and template-kit-candidates applied, without `node_modules` or `dist`, then run `npm install` at the project root: its `workspaces` already list `src-app/mfe_packages/*`, and `shared/` needs no entry. List the two guidelines in the project's own AI bundle; they cite only paths under `src-app/mfe_packages/`. A project that drops the contacts screen moves `inbox-contacts-mfe/src/shared-inbox/` into a package it keeps, or the shared folder loses its test coverage. The packages reference nothing outside this template's directories.
