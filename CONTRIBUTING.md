# Contributing

## Sign-off and branches

Every commit requires a Developer Certificate of Origin sign-off: commit with `git commit -s`, which adds the `Signed-off-by:` trailer with your name and email. The requirement is enforced by the DCO check configured on the hosting repository, which does not exist yet; until then the sign-off is the contributor's responsibility.

The repository has one long-lived branch, `main`. Work happens on a short-lived branch and reaches `main` through a pull request; the CI workflow runs on every pull request and push to `main`.

## Layout

Every top-level directory carrying `frontx-template.json` is a template (manifest presence, never a name guess; `scripts/template-discovery.mjs` is the one place that rule lives). Every template has the same shape (`architecture/DESIGN.md` section 4.2): an overlay that claims only `src-app/mfe_packages/<package>/`, an optional `src-app/mfe_packages/shared/<name>/`, a non-screen package `src-app/verify_packages/<package>/` (template-site-meta's `site-meta`, template-site-brand's `site-brand`, template-kit-candidates' `kit-candidates`, template-site-blocks' `site-blocks`; the root `.gitignore` lists each site copy, and other packages depend on it by name and exact version, never by path), and its own AI bundle `.frontx/ai/@gears-frontx/frontx-template-<name>/`. A template has no `package.json`, no lockfile and no test harness of its own; the site is the harness.

`site/` is the FrontX application. Its shell files come from template-shell through the FrontX CLI. The site rebuilds the shell's layout on React and `@gears-frontx/ui-kit` (`architecture/DESIGN.md` section 4.3.4): every shell file it changes, adds or removes is listed in `scripts/shell-changes.mjs`, which keeps the same lists for template-mfe and template-design-guardrails, and `npm run shell:changes -- --check` fails when a list and `site/` disagree against the pristine template. Every other applied file stays as it ships, apart from one adaptation every applied text file carries: a long dash becomes `-`. After a template upgrade, `npm run shell:changes -- --adapt` writes the adaptation; the check fails on an applied file that lacks it. `site/package.json` also carries the dependency delta that pins the FrontX registry packages at their released versions and declares `concurrently`, which the shell's `dev:all` runs through `npx` (section 4.8).

`scripts/`, `assets/`, `.github/`, `.cf-studio/` and `architecture/` belong to the repository, not to the site or a template.

## Single-source rule

Screen code is committed only inside its template. `site/src-app/mfe_packages/` is a composition product: `npm run site:assemble` copies each template's subtrees there, and template-shell's `.gitignore` keeps it out of git. Never edit a file under `site/src-app/mfe_packages/`; edit the template and assemble again. `npm run site:assemble -- --check` fails and names every file that differs from its template.

## Development loop

```bash
npm ci
npm run setup                       # site:assemble + npm ci --prefix site
npm run site:assemble -- --watch    # in one terminal: re-copy on template edits
npm run dev                         # in another: the site at http://localhost:5173/?screen=home
```

`npm run dev` builds the packages and MFEs first, so the host answers after a minute or two; `/` opens the home screen. `npm run dev:smoke` runs the same `npm run dev`, waits until the host and every remote entry answer, and stops everything it started; run it after changing a package's scripts, ports or dependencies, or `site/package.json`. A tool the shell runs through `npx` must be declared in `site/package.json`: if it is not, npx asks to download it and `npm run dev` waits on that prompt with nothing listening.

A new screen is created inside a `template-*` directory, starting from template-mfe's `_blank-mfe` or an existing site package (the FrontX CLI has no package scaffold command yet), with its `seo` block in `mfe.json`; a demo screen declares `presentation.group: "demos"`. Pages are configuration over blocks: kit components first, kit candidates (`@gears-frontx/kit-candidates`) for the parts the kit lacks, and the blocks of `@gears-frontx/site-blocks` for every arrangement; a section the blocks cannot draw becomes a new block there, never page styling. The templates screen's pages, the docs screen's version data and the libs screen's library data are generated: after changing a template manifest, `template-site/.../site-templates-mfe/src/content/guide.json` or the pins, run `npm run site:data` (it asks the npm registry for the commit each pinned release was published from). After adding a package, run `npm run site:assemble` and `npm install --prefix site` once to record it in `site/package-lock.json`. Lockfiles are written with npm 10.9.4, the `packageManager` pin (`npm install -g npm@10.9.4`; CI installs the same version and checks `npm --version`). When npm rewrites the entry `node_modules/@gears-frontx/frontx-template-shell` of `site/package-lock.json`, restore it to `{ "resolved": "", "link": true }` (`architecture/DESIGN.md` section 4.3.3). Change the root lockfile with `npm install` while the lockfile is present: npm 10.9.4 cannot resolve it from scratch (section 4.1).

## Rules for repository content

- English in every file and no long dashes (only "-"). No hard line wraps inside paragraphs. The site is a Constructor Fabric property: the company name, its product names, its brand domain and its GitHub organization are welcome, and the header and footer carry the Constructor Fabric lockup. `npm run policy:text` (part of `npm run lint`) refuses, over the scope below, the long dashes, a design-tool vendor name, the company's internal mail and host domains (the public homepage `https://constructor.tech/`, written exactly so, is allowed), a company-specific workspace name and the former product name. The rule that FrontX names no company belongs to gears-frontx upstream.
- Template code and the shell files the site owns use `@gears-frontx/ui-kit` components first and style with CSS Modules on its tokens: no Tailwind, no `@apply`, no class name as a string literal. `npm run policy:own-styles` enforces it; files copied from the kits' demos are exempt by path (`EXEMPT_PATHS` in `scripts/policy-own-styles.mjs`). Whoever owns a file, the policy also refuses Tailwind in the shell's build: a Tailwind package in `site/package.json` or a template's `package.json`, a Tailwind or PostCSS config file anywhere under `site/`, and a Tailwind import, directive or `@apply` in any shell source or config file.
- The visual layer has three tiers: the brand (template-site-brand's tokens and art), kit candidates for the primitives the kit lacks, and blocks (`template-site-blocks`, and the blocks folders of template-inbox, template-mfe-demo and template-catalogue) whose stylesheets are layout on tokens. `npm run policy:own-styles` also holds that rule: a composition (a screen, page, route, renderer or lifecycle) imports no stylesheet, the kit's `theme.css?inline` aside in a file that anchors it with `anchorKitThemeOnShadowHost`, and passes no `style` prop and no `className` other than a kit variants call (`buttonVariants(...)`) or its own forwarded `className`; a block, a screen frame or a shell chrome stylesheet (`site/src-app/app/layout/`, `mfe/`, `globals.css`) declares only layout properties (box, position, flex and grid, overflow, containment, scroll margins, the list marker reset) on tokens, keywords, `0`, percentages, `fr` and `auto`, and every other declaration needs a row in its exemptions ledger (`styles-exemptions.json` beside the blocks, `site/src-app/app/layout/styles-exemptions.json` for the chrome) naming the kit gap or defect it waits for; a row whose file, selector or property is gone fails, and so does a hex colour anywhere outside `brand.json`, the files generated from it and the brand art palettes (a mask's stops aside). Close a gap by deleting its rows with the declarations, never by widening the allow-list.
- `npm run verify:ui` runs template-design-guardrails' design-defect checker (axe-core and the layout rules) over every page of the built `seo-manifest.json`, every block showcase route and the not-found screen, at 1440 and 390 pixels in the light theme, against `npm run dev` (started for the run unless one already answers); it needs `npm run build` first. Only a finding that `scripts/design-verify-baseline.json` does not carry fails; a finding whose generated React id (`#_r_1n_`, `#base-ui-_r_8_`) moved between runs is the carried one. Every carried finding names its reason, a G34 checker false finding or a kit defect with its GAPS row, and `npm run verify:ui:baseline -- check` fails one that does not. To rebuild the baseline after a fix, run `npm run verify:ui -- --no-baseline`, then `npm run verify:ui:baseline -- build design-verify-report/findings.json`, which refuses a finding no rule in `scripts/design-verify-baseline.mjs` knows: fix that one instead. Dark states mean something only under `npm run dev`, whose Studio overlay restores the stored theme (`npm run verify:ui -- --themes light,dark`); the production build always paints light, and CI gates the light theme.
- Every MFE package pins the ecosystem, the shell's workspaces, the packages this repository's templates deliver and the shared toolchain exactly; `npm run policy:pins` reads the expected versions from the direct `@gears-frontx/*` dependencies of `site/package.json` (exact registry versions only), the applied shell, and each `@gears-frontx/*` package under a template's `src-app/verify_packages/` (its own version, which `site/package.json` must repeat when the site application depends on it).
- The kit theme helpers (`anchorKitThemeOnShadowHost.ts`, `kitThemeScope.ts`) are template-mfe's per-package helpers: every copy in a template stays code-identical to the copy template-mfe ships, apart from its own comments and `@cpt-` markers, and `scripts/kit-theme-helpers.test.mjs` (part of `npm run test:unit`; it reads template-mfe from the CLI inventory `npm run site:data` installs) fails on a copy whose code drifted. A fix goes upstream and is copied back.
- The site's brand values live once, in template-site-brand's package; `npm run brand:check` (part of `npm run lint`, run on the composed site copy) holds the generated token files to their source, contrast at 4.5:1 and the head colours in `site.config.json`; after editing the package's `src/brand.json`, `npm run brand:generate` rewrites the generated files in the template.
- A copied file is adapted where it conflicts with these rules, and the template README lists each adapted copy with its source commit.
- Scope of the text scans: the long-dash rule holds in every text file of the repository except installs and build output (`node_modules/`, `dist/`, `coverage/`), `.cf-studio/` and the applied files under `site/` included. The other rules leave out `.cf-studio/` (Studio-owned) and the files template-shell, template-mfe and template-design-guardrails applied to `site/` that the site left as they ship. Those stay as the official templates ship them apart from the long-dash adaptation (`architecture/DESIGN.md` sections 4.3.1 and 4.3.4); any other finding in them is reported upstream, not edited here. The applied files the site changed or added are in scope. Lockfile integrity hashes and generated asset names can match a name pattern by chance and are not findings.

## Validation

```bash
npm run templates:validate
npm run catalogue:check
npm run setup
npm run policy:pins
npm run site:data -- --check
npm run shell:changes -- --check
SITE_ORIGIN=http://localhost:4173 npm run build   # a production build reads origin from site.config.json instead
npm run seo:check
npm run type-check
npm run lint
npm run arch:deps
npm run test:unit
npm run dev:smoke
npm run verify:ui:baseline -- check
npm run verify:ui                                 # after the build; about half an hour
python3 .cf-studio/.core/skills/studio/scripts/studio.py validate
python3 .cf-studio/.core/skills/studio/scripts/studio.py spec-coverage --system <slug>   # per system; CI adds --min-coverage and --min-granularity
```

CI (`.github/workflows/main.yml`) runs the same sequence on Node 24.14.x and 25.x with `SITE_ORIGIN=http://localhost:4173`, the `verify:ui` gate as its own job on Node 24.14.x once that passes, and the Studio validation on Python 3.12 (`studio.py` needs Python 3.11 or later). The Studio validation checks the root artifact tree in `architecture/` and each template's own tree in `<template>/architecture/`, every kind in FULL traceability, and the `@cpt-` markers in the code paths the registry lists: a marker binds only to the ids of its own tree, and a `cpt-frontx-*` marker anywhere binds nothing (`architecture/ADR/0001-template-territory-traceability.md`). The Studio spec coverage job measures the marker coverage of each system's registered code (`site` and the nine `template-<name>` systems) and fails when a system falls under its floors in `.github/workflows/main.yml`, which sit just under the current values; raise a floor when a change raises the coverage, and add markers rather than lower one (`architecture/DESIGN.md` section 4.9). Three floors sit lower than they once did, each for a recorded reason: template-site's coverage floor (73) dropped when its component library, code carrying many markers, was deleted for the blocks of template-site-blocks, and its granularity floor (0.68) when its content model took the action row from template-site-blocks, an import line outside any marker block; template-site-brand's granularity floor (0.56) dropped when its brand art arrived, whose drawing code sits in long marker blocks that splitting would only make artificial.

The FrontX ecosystem packages are installed from the npm registry at exact released versions. To take a new release, move every pin of the package at once (`npm run policy:pins` names any pin left behind), update both lockfiles as described above and run `npm run site:data` (`architecture/DESIGN.md` section 4.8).
