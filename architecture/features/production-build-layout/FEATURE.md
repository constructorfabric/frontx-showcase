## 1. Feature Context

- [x] `p2` - `cpt-site-feature-production-build-layout`

### 1.1 Overview

The production build is one static folder, `site/dist/`, that holds the host document, the manifest aggregate, every remote under `mfe/<package>/` and the generated metadata outputs. After the host build, `npm run site:dist` copies every remote the aggregate names into that folder and rewrites each remote's `publicPath` relative to the aggregate; at run time the host's registration bootstrap fetches the aggregate from the build base resolved against the document, and the MFE handler of `@gears-frontx/mfes` resolves each relative `publicPath` against the document, which sits in the same folder as the aggregate, so the same folder works at the root of an origin and under any sub-path. The bootstrap's screen domain mount handler also reports a failed load or mount to the shell layout's failure store.

### 1.2 Purpose

Hosting is not chosen yet, and the shell's build fetches the aggregate from a fixed place while its generator writes absolute remote addresses; the site must be publishable anywhere without a rebuild. The build sequence (`npm run build`: compose, the shell build, `site:dist`, then the metadata outputs generated by template-site-meta's command line from `site.config.json`, the screens' `seo` blocks and the raster record `assets/rasters.json` of `assets/og-image.svg`) is declared in the root `package.json`, which carries no markers; the generator, its outputs and the metadata check are specified in [template-site-meta DESIGN](../../../template-site-meta/architecture/DESIGN.md). The root's share of the metadata requirements is the site-level values declared once in `site.config.json` and the build step that derives every output from them. The relative build base itself is set in `site/vite.config.ts`, a configuration file the registry ignores.

**Requirements**: `cpt-site-fr-static-build`, `cpt-site-fr-metadata-single-source`, `cpt-site-fr-discovery-files`

**Principles**: `cpt-site-principle-metadata-once`

## 2. Actor Flows (CDSL)

### Lay out the production build

- [x] `p2` - **ID**: `cpt-site-flow-production-build-layout-lay-out-dist`

**Actor**: `cpt-site-actor-site-developer`

**Use case**: `cpt-site-usecase-change-screen`

**Success Scenarios**:
- After the host build, every remote of the aggregate sits in `site/dist/mfe/<package>/` without the files the host never reads, every `publicPath` in the aggregate reads `mfe/<package>/`, and the command names the packages it laid out.

**Error Scenarios**:
- `site/dist/` holds no aggregate: the command refuses before it writes, naming the missing file.
- The aggregate names a manifest no built package carries: the command refuses before it writes, naming the manifest.

**Steps**:
1. [x] - `p2` - The developer runs `npm run site:dist` (or `npm run build`, which runs it after the host build); the command lays out the site directory of the repository - `inst-run-layout`
2. [x] - `p2` - **IF** `site/dist/` has no manifest aggregate, refuse before writing anything - `inst-if-no-aggregate`
3. [x] - `p2` - Read the aggregate's configs and index the built packages under `site/src-app/mfe_packages/` by the manifest id their build's enriched manifest carries, skipping the shared folder and dot entries - `inst-index-built`
4. [x] - `p2` - **FOR EACH** aggregate config, find its package; **IF** no built package carries its manifest id, refuse before writing anything - `inst-if-unknown-manifest`
5. [x] - `p2` - Remove any previous `dist/mfe/` layout, so the result replaces rather than merges - `inst-clear-layout`
6. [x] - `p2` - **FOR EACH** laid-out package, copy its build into `dist/mfe/<package>/` without the preview page, the federation types, the build statistics and the enriched manifest, and set the `publicPath` of its manifest and of every entry's manifest to `mfe/<package>/` - `inst-copy-and-rewrite`
7. [x] - `p2` - Write the aggregate back and **RETURN** the package directories in aggregate order - `inst-write-aggregate`
8. [x] - `p2` - Print the laid-out packages; **IF** the layout refused, print its message and exit with a failure - `inst-report`

### Load the screens at any mount point

- [x] `p2` - **ID**: `cpt-site-flow-production-build-layout-load-screens`

**Actor**: `cpt-site-actor-visitor`

**Use case**: `cpt-site-usecase-visit-page`

**Success Scenarios**:
- The visitor opens the built site at the root of an origin or under a sub-path; the host reads its own copy of the aggregate next to the document, registers every package with the remote addresses the aggregate writes and mounts the screens the address names.

**Error Scenarios**:
- The aggregate does not answer: bootstrap fails with the address and status, and the shell layout shows its bootstrap failure state.
- The aggregate is empty: bootstrap warns and registers no package.

**Steps**:
1. [x] - `p2` - **IF** the app has no MFE registry, fail the bootstrap - `inst-if-no-registry`
2. [x] - `p2` - Register the host chrome action schemas on the registry's type system - `inst-register-chrome-schemas`
3. [x] - `p2` - Register the screen domain, opted into the two chrome actions and built with the failure-reporting mount handler, and the sidebar, popup and overlay domains - `inst-register-domains`
4. [x] - `p2` - Broadcast the current theme and language as shared properties - `inst-broadcast-properties`
5. [x] - `p2` - Resolve the aggregate's address from the build base against the document's address - `inst-resolve-aggregate-url`
6. [x] - `p2` - Fetch the aggregate; **IF** it does not answer successfully, fail the bootstrap naming the address and status - `inst-fetch-aggregate`
7. [x] - `p2` - **IF** the aggregate lists no package, warn and **RETURN** - `inst-if-empty`
8. [x] - `p2` - Register every package's non-action schemas first, so a leaf package's extensions validate through schemas a parent package declares whatever the aggregate's order - `inst-register-non-action-schemas`
9. [x] - `p2` - **FOR EACH** package, register its declared action schemas, its manifest, its domains, its entries and the extensions of domains the host owns, putting an extension of a domain another runtime owns only on the type system - `inst-register-packages`
   1. [x] - `p2` - Register the package's schemas whose id is an action its entries declare (a screen's show action among them) - `inst-register-action-schemas`
   2. [x] - `p2` - Register the package's manifest, its domains and its entries on the type system - `inst-register-declarations`
   3. [x] - `p2` - Register each extension of a domain the host owns with the registry, and put an extension of a domain another runtime owns only on the type system, which every runtime of the page shares - `inst-register-extensions`

## 3. Processes / Business Logic (CDSL)

### Report a failed screen mount

- [x] `p2` - **ID**: `cpt-site-algo-production-build-layout-report-mount-failure`

**Input**: A `mount_ext` action on the screen domain: its subject and its history intent.

**Output**: The screen mounted and the failure report cleared, or the failure reported and the action still failed.

**Steps**:
1. [x] - `p2` - **TRY** mount the subject through the screen domain's exclusive mount strategy - `inst-try-mount`
2. [x] - `p2` - **CATCH** a failed load or mount: report the subject and the history intent (`replace` and `none` kept, anything else `push`) to the shell layout's failure store and rethrow, so the action still fails - `inst-catch-report`
3. [x] - `p2` - Clear the failure report after a successful mount - `inst-clear-on-success`

### Resolve the remote addresses

- [x] `p2` - **ID**: `cpt-site-algo-production-build-layout-resolve-addresses`

**Input**: The build base, the document's address, a laid-out package's folder name.

**Output**: The aggregate's absolute address; each remote's production `publicPath`.

**Steps**:
1. [x] - `p2` - Join the build base, given a trailing slash, with the aggregate's file name and resolve the result against the document's address - `inst-aggregate-address`
2. [x] - `p2` - Write each remote's production `publicPath` as its folder under `mfe/`, relative to the aggregate, with a trailing slash - `inst-relative-public-path`

## 4. States (CDSL)

### No Lifecycle to Model

The layout step and the registration bootstrap run once each and keep no entity with a lifecycle; the failure state the mount handler reports into is specified by the shell layout and navigation feature.

## 5. Definitions of Done

### Self-contained, relative dist layout

- [x] `p2` - **ID**: `cpt-site-dod-production-build-layout-dist-layout`

The system **MUST** lay out every remote the manifest aggregate names under `site/dist/mfe/<package>/` with its `publicPath` relative to the aggregate, **MUST** refuse an unknown manifest id or a missing aggregate before it writes, and **MUST** give the same result on every run.

**Implements**:
- `cpt-site-flow-production-build-layout-lay-out-dist`
- `cpt-site-algo-production-build-layout-resolve-addresses`

**Touches**:
- API: `npm run site:dist`, `npm run build`
- Entities: Screen MFE package

### Mount-independent registration

- [x] `p2` - **ID**: `cpt-site-dod-production-build-layout-mount-independent-bootstrap`

The system **MUST** fetch the manifest aggregate from the build base resolved against the document and register every relative remote address as the aggregate writes it, for the MFE handler to resolve against the document, so one build works at the root of an origin and under any sub-path with no origin or path fixed at build time.

**Implements**:
- `cpt-site-flow-production-build-layout-load-screens`
- `cpt-site-algo-production-build-layout-resolve-addresses`

**Touches**:
- API: `GET ./generated-mfe-manifests.json`, `npm run preview`
- Entities: Screen MFE package, Site config

### Failed mounts reported to the page

- [x] `p2` - **ID**: `cpt-site-dod-production-build-layout-failure-report`

The system **MUST** report every failed load or mount of a screen to the shell layout's failure store with the failed action's history intent while the action still fails, and **MUST** clear the report when a screen mounts.

**Implements**:
- `cpt-site-algo-production-build-layout-report-mount-failure`

**Touches**:
- API: `mount_ext` on the screen domain
- Entities: Screen extension

## 6. Acceptance Criteria

- [x] `npm run site:dist` copies every aggregated remote without the build leftovers, leaves out a built package the aggregate does not carry, rewrites every `publicPath` to the remote folder, replaces a previous layout and refuses an unknown manifest or a missing aggregate (`scripts/site-dist.test.mjs`).
- [x] The bootstrap resolves the aggregate from the build base against the document, fetches it from there and registers a relative `publicPath` as the aggregate writes it, and an absolute one unchanged (`site/src-app/app/mfe/bootstrap.test.ts`, "production layout addressing").
- [x] The bootstrap registers the four base domains before fetching, throws when the fetch fails and registers schemas, manifest, entries and the host's extensions per package (`bootstrap.test.ts`).
- [x] A failed screen mount is reported with its screen and still fails the action; the report clears once a screen mounts (`bootstrap.test.ts`, "screen load failures").
- [x] `npm run build` followed by `npm run preview` serves every address of DESIGN section 4.5 from `site/dist/`, with the generated discovery files beside the host.
