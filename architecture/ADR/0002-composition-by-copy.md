**ID**: `cpt-site-adr-composition-by-copy`

## Context and Problem Statement

Every screen of the site, and the page metadata tool, live in this repository's templates: top-level directories with a `frontx-template.json` manifest whose `exclusiveSubtrees` name the paths each template claims inside a project. The site in `site/` is a FrontX application seeded from template-shell, and template-shell runs, builds, tests and registers only what sits in its own workspace roots: its scanners, its `dev:all` script and its manifest generator read `site/src-app/mfe_packages/*`, its npm workspaces are `packages/*`, `src-app/mfe_packages/*` and `src-app/verify_packages/*`, and every package reaches the shell's test base and test utilities through relative paths (`../../vitest.mfe.base`, `../../__test-utils__`) that resolve only from `site/src-app/mfe_packages/<package>/`. template-shell's own `.gitignore` already ignores `src-app/mfe_packages/*` as content "regenerated by the documented compose step". How does a template's code get into the site so that the site runs and builds it, while the code is edited and committed in one place only?

## Decision Drivers

* **One committed copy of screen code** - two committed copies of a screen drift apart; the requirement is that screen code is committed only inside its template and that the site's copy is checkable for drift.
* **The shell stays as it ships** - the composition must work with template-shell's workspace roots, scanners and relative paths, not with a modified shell.
* **The FrontX CLI cannot apply these templates from the working tree** - the CLI at `0.3.0` acquires templates only by a `github:` source-spec with a host and a ref; it has no local-path source-spec, and this repository is not published.
* **Module resolution must find the site's install** - a package's imports (`react`, `@gears-frontx/*`) must resolve from `site/node_modules`, since a template has no `package.json` or install of its own.
* **Developers edit the template, never the copy** - a change made in the composed copy must be caught, not silently overwritten or silently kept.

## Considered Options

* **Copy the claimed subtrees into the site with a recorded ledger** - a repository script copies every claimed path of every template into the same path under `site/`, records what it wrote, refuses to overwrite paths it did not create, reports drift both ways with a check mode and re-copies on edits in a watch mode; the copies are git-ignored.
* **Symlink the template packages into the site** - each claimed path under `site/` is a symbolic link to the template directory.
* **Commit the packages inside `site/` and drop the templates' copies** - the site is the only home of the screen code, and the templates are produced from it when needed.
* **Apply the templates with the FrontX CLI** - `frontx add` applies each template into `site/` and writes a provenance record, as for the official templates.

## Decision Outcome

Chosen option: "Copy the claimed subtrees into the site with a recorded ledger", because it is the only option that keeps one committed copy, works with template-shell exactly as it ships and needs nothing the CLI or the bundler does not provide today.

**Composition is a copy made by the repository's compose step.** `npm run site:assemble` copies each template's `exclusiveSubtrees` into the same paths under `site/`: the screen packages into `site/src-app/mfe_packages/`, the template-delivered tooling package into `site/src-app/verify_packages/`, the AI bundles into `site/.frontx/ai/`. Installs and build output are never copied. It records every file it wrote with its SHA-256 in `site/src-app/mfe_packages/.assembled.json`, removes on the next run what it wrote before and no template claims any more, and refuses to overwrite a path it did not create. `--check` reports drift both ways without writing, including any entry of the composition directory that no template claims; `--watch` re-copies on template edits.

**The template is the only committed copy.** template-shell's `.gitignore` keeps `site/src-app/mfe_packages/*` out of git, and the root `.gitignore` does the same for the composed AI bundles and tooling package. No symbolic link is used anywhere in the composition.

The scope of this decision is how this repository's templates reach `site/`. It does not decide how the official templates are applied (the FrontX CLI applies them, with provenance), what a template may claim (the uniform shape), or what becomes a template ([0004](./0004-template-or-repository-tooling.md)).

### Consequences

* Good, because screen code is edited and reviewed in one place, and `site:assemble --check` in CI fails on any drift between a template and the site.
* Good, because template-shell needs no change: its workspace roots, scanners, manifest generator and relative test paths find the composed packages where a seeded project would hold them.
* Good, because imports in a composed package resolve from the site's install, exactly as they would in any project the template is applied into.
* Good, because the ledger makes composition safe to repeat and safe next to files the CLI applied: the step never touches a path it did not create.
* Bad, because a developer can edit the composed copy by mistake; the edit is lost on the next composition unless `--check` reports it first. The guideline in each template's AI bundle and the README say to edit the template only.
* Bad, because every edit needs a composition step before the site sees it; `--watch` covers the development loop.
* Bad, because no provenance record exists for these templates in `site/`: the template and the site are one commit, so the record would carry no baseline the repository does not already hold.

### Confirmation

`npm run site:assemble -- --check` runs in CI and fails on drift in either direction. `scripts/site-assemble.test.mjs` covers copying, the ledger, refusal to overwrite unowned paths, removal of unclaimed paths and the check mode. Review confirms that no symbolic link is added under `site/` and that no composed path is committed.

## Pros and Cons of the Options

### Copy the claimed subtrees into the site with a recorded ledger

* Good, because it composes exactly what each manifest claims, the same paths the CLI would write when the template is applied elsewhere.
* Good, because the check mode turns "the site's copy equals the template" into a CI gate.
* Neutral, because it is repository tooling with its own tests, about the size of the CLI's own apply step for exclusive subtrees.
* Bad, because the copy exists on disk and invites editing in the wrong place.

### Symlink the template packages into the site

* Good, because there is no copy to drift and no composition step to run.
* Bad, because Vite resolves real paths by default, so a symlinked package resolves `react` and every other import from inside the template directory, which has no `node_modules`; the build fails or picks up a second copy of a package.
* Bad, because the relative paths to the shell's test base and test utilities then resolve from the template directory, outside the site.
* Bad, because symbolic links behave differently across platforms and archive tools, and a template copied out of the repository carries no link target.

### Commit the packages inside `site/` and drop the templates' copies

* Good, because the shell sees ordinary packages and no step is needed.
* Bad, because template-shell's `.gitignore` ignores that directory in every seeded project; committing there means editing the shell's ignore rules.
* Bad, because the templates stop being the home of their code, so a template can no longer be validated, copied or published on its own.

### Apply the templates with the FrontX CLI

* Good, because it is the FrontX way to apply a template, with a provenance record and the CLI's own ownership checks.
* Bad, because the CLI at `0.3.0` has no local-path source-spec: its spec parser requires a host and a ref, and its local fetcher is a test-only seam, so it cannot apply a template from this working tree.
* Bad, because until the repository is published there is no source-spec to point at, and every change would need a commit and a fetch before the site sees it.

## More Information

template-shell's `.gitignore` names `src-app/mfe_packages/*` as content a compose step regenerates; this decision supplies that step. When the FrontX CLI gains a local-path source-spec, or once this repository is published, applying the templates with the CLI becomes viable and this decision should be revisited. The decision is also revisited if Vite or template-shell changes how packages are resolved so that a link would resolve imports from the site.

Applicability of the remaining checklist categories: **PERF** - Not applicable, because the copy runs at development and build time only and adds no runtime path. **SEC** - Not applicable, because no secret or authentication surface is involved. **REL** - addressed: the ledger makes the step idempotent and refuses to overwrite unowned files. **DATA** - Not applicable, because no data schema is fixed. **INT** - addressed: the integration contract is the template manifest's `exclusiveSubtrees`, the same contract the CLI applies. **OPS** - addressed: CI runs the check mode. **MAINT** - addressed: one committed copy per package. **TEST** - addressed: the step has its own tests, and every composed package runs its tests in the site's harness. **COMPL** - Not applicable. **UX** - addressed for the developer: `--watch` keeps the development loop to one edit. **BIZ** - Not applicable.

This decision directly addresses the following requirements and design elements:

* `cpt-site-fr-single-copy` - Screen code is committed only in its template, and the site's copy is produced by composition and checked for drift.
* `cpt-site-usecase-change-screen` - A change made in a template reaches the site through the compose step.
* `cpt-site-principle-single-source` - The composed copies are git-ignored and compared with the templates by the check mode.
* `cpt-site-component-site-assemble` - The compose step this decision chooses.
* `cpt-site-constraint-site-own-project` - The site is installed as its own npm project, so the composed packages join its workspaces and resolve from its install.
